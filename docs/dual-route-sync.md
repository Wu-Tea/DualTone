# 双路同步

在主面板主音频旁打开「同步设置」，选择「双路同步」，再选择已安装的虚拟声卡播放端作为入口。系统声音先进入虚拟端点，DualTone 通过 WASAPI 回环读取，再分别播放到主、副设备。无需新建自有驱动；程序包不包含虚拟声卡驱动。

主音频保留原声，只增加可调延迟；副音频继续使用已有 EQ、多段过滤、空间补充或混响。静音对比仅静音副路。路由或设备更改需要先停止，主路延迟和声音参数可播放中调整。

## 试听

1. 主面板选择实际主音箱与副设备。
2. 在同步设置中选择虚拟入口。不要选择会在别处直接发声的物理输出；入口与两台输出必须不同。
3. 开始播放。Windows 普通和多媒体默认输出切到入口，通信默认设备不变。固定输出设备的应用要手动选择同一个入口。
4. 从主路延迟 0 ms 开始，根据听感逐步增加。数字输入可精确填写 0–1000 ms；按钮每次调整 5 ms，滑条方向键每次 1 ms。
5. 正常停止、关闭程序或音频线程报错时，恢复仍由 DualTone 占用的默认输出；用户播放期间手动换过的默认设备不覆盖。

延迟值是**额外添加到主路的时间**，不是测出来的总延迟。两路仍有设备和软件缓冲；无法仅从 Windows 队列得知蓝牙传输、显示器处理或声音传播时间。本版不自动进行麦克风校准，也不把时钟漂移控制当成自动听感对齐。只能延后主路；如果主路本来就更晚，需要先调整设备组合。

混响包含刻意产生的反射和尾音，不应把尾音起点强行对齐原声。游戏使用高延迟副设备时，延迟主路会增加整体操作到声音的等待。旧的数字转发测量只适用于直出模式，避免在新路由上生成误导性结果。

应用被强制结束、系统崩溃时无法运行恢复逻辑；可在 Windows 声音设置中重新选择物理主音箱。虚拟驱动自带的监听/转发应关闭，否则可能另外播放一份原声。

## CLI 与持久化

```powershell
.\DualToneCLI.exe devices
.\DualToneCLI.exe set --json '{"routing_mode":"sync","input_id":"虚拟播放端的设备 ID","main_delay_ms":40}'
.\DualToneCLI.exe start
.\DualToneCLI.exe set --json '{"main_delay_ms":45}'
.\DualToneCLI.exe status
.\DualToneCLI.exe stop
.\DualToneCLI.exe set --json '{"routing_mode":"direct"}'
```

`source_id` 继续表示物理主音频，`target_id` 表示副音频，`input_id` 只在同步模式使用。所有值来自 `devices`，不能将名称当作 ID。停止时可以更改或清除入口（`input_id: ""`）。配置 version 4 可读取 1–3，首次保存前保留旧版备份；升级默认仍为 `direct`，不自动改变系统输出。声音预设切换和导入保留当前设备、模式和主路延迟，避免声音预设意外改变系统路由。

## 实现与验证

主路延迟在 48 kHz 内部时基上使用立体声环形缓冲；修改时在旧、新抽头间做 10 ms 交叉淡化。主路不经过副路 EQ、增益或混响，但必要的格式转换和时钟校正仍会重采样，不承诺逐位透传。

两路各自以设备事件驱动渲染，不互相阻塞。采样率转换之后，每路有目标 20 ms 的抖动队列，利用平滑的占用误差进行不超过 ±2000 ppm 的时钟速率修正。真实欠载会输出静音并重新积累缓冲，计入 `main_underruns` / `auxiliary_underruns`；超过 250 ms 积压则报错停止，避免无限累积延迟。设备提交缓冲另计。常量集中在 `core.hpp`，不在 GUI 或设备名称中藏参数。

`verify_sync.py` 覆盖立体声延迟因果性、最大延迟、分包一致性、实时调整、模拟十分钟 ±1000 ppm 时钟偏差、配置迁移、预设/导入的路由隔离和 GUI 显示。`verify_sync_devices.py` 是显式运行的本机测试，会短暂切换默认输出并播放低音量信号，核对实际延迟变化、停止恢复、用户覆盖和启动失败；最终恢复原输出。测试不作为任意硬件声学同步保证。


### 2026-11-24 本机验证

18 项自动测试通过，包含原有 DSP/采样率转换、混响、命名管道和新同步功能。虚拟入口回环输入 96 kHz，主、副输出各 48 kHz；主路设置由 0 改为 80 ms，独立数字录音的相对变化约 77.5 ms。录音以数据到达时间近似起点，约几毫秒误差，不包含扬声器到耳朵的完整声学延迟。

完成声音输入、静音、恢复输入与额外 35 秒静音运行；后一轮主副欠载和输入不连续均为 0，队列总量最高 52 ms（包含端点提交缓冲，不包含设定的主路延迟）。停止恢复、用户在运行中改默认设备、入口失效启动失败均通过；原用户声音配置与通信输出未修改。

测试曾发现静音补包以实际唤醒时间重新计时时会逐渐少发样本，导致欠载；已改为固定时间线推进，并复测以上场景。这里没有将额外增大缓冲作为该问题的修复。
